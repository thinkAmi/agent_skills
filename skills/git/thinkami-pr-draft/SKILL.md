プルリクのタイトルと本文の**案**を作ります。以下の規約と手順に従ってください。

このスキルの成果物は案であり、PR そのものではありません。人間が案を受け取り、
手を入れてから PR を作ります。`gh pr create` は実行しません。

対象は thinkAmi / thinkAmi-sandbox の自リポジトリです。他者のリポジトリへの
PR は相手の規約に従うため、このスキルの対象外です。

## 読み手

優先度の高い順に「いまのレビュアー」「未来の自分」「AI エージェント」です。
コミット規約(`thinkami-git-commit`)とは順位が違います。PR 本文は
レビュアーの作業を設計するためにあり、履歴の Why は各コミットが担います。

見出し名は全 PR で固定し、スキルを知らない人が名前だけで意図を読めるようにします。

## 規約

キーワード MUST / SHOULD / MAY は RFC 2119 の意味で使います。

### タイトル

- その PR で何をしたかを 1 文で書き、動詞で終える(MUST)
  - 例: `エピソード一覧の公開日に年を表示する`
- Conventional Commits の type / scope は付けない(MUST)
  - 一覧で見たときに邪魔になるだけで、自リポジトリでは意味を持たない
- 複数のまとまりが入る PR は「大きな主題(A・B・C)」の形にしてよい(MAY)
  - 主題が立たないほど無関係な相乗りなら、それはタイトルではなく PR 分割の合図。
    その旨をユーザーに伝える

### 本文の骨格

見出し名と順序は固定です(MUST)。

```
## 背景              MAY
## なぜ              MUST
## やったこと        MUST
## やっていないこと  MAY
## 動作確認          MUST
── ここまで必読 ──
## スクリーンショット MAY(例外あり、後述)
## 補足              MAY
## 関連              MAY

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

- 該当のない MAY 見出しは見出しごと消す(MUST)。空欄や「なし」を残さない
  - 例外はスクリーンショットのみ(後述)
- MUST の見出しはすべてスクリーンショットより上にある。読み手は
  「画像より上は必読、下は任意」と読める

#### 背景(MAY)

この PR を起こす前から存在していた事実。現状、制約、起きた事故、判明した
挙動など。

- 判定基準: **この PR をやると決める前に書けた文か**。書けたなら背景、
  書けないなら「なぜ」
- 背景が短ければ見出しを省き、「なぜ」だけで成立させてよい

#### なぜ(MUST)

その事実を受けて、この PR が何を判断したか。動機、制約、採らなかった案とその
理由。

- 背景と混ぜない。背景が長いほど判断が埋もれるので、分けて短く言い切る
- 「なぜ」を省いて「背景」だけ、は認めない
- 複数のまとまりが入る PR で共通の判断が無い場合は、「## なぜ」を立てず、
  「やったこと」の各小見出しの冒頭で判断を書いてよい(分散)。
  どこにも判断が無い状態は不可

#### やったこと(MUST)

最終状態を「いま、こう動く」で書く。経緯や「〜を修正した」ではなく状態で。

- 意味のまとまり(独立して説明できる機能や決定)ごとに `###` 小見出しを立てる
  - OpenSpec を使うリポジトリなら change 名が自然にまとまり名になる。
    使わないリポジトリでは機能名や振る舞いの名前を付ける
  - まとまりが 1 つなら小見出しを立てず、見出し直下に書く
- 実装時の行き来や流れは書かない。最終的にどうなったかが分かりにくくなる
- diff の再掲をしない。変更ファイルの列挙は Files changed が既に見せている

#### やっていないこと(MAY)

スコープ外と決めたこと、次の候補。「やったこと」と対で読めるように書く。

#### 動作確認(MUST)

何を・どう確認したかを、レビュアーが再現できる粒度で「確認 → 期待結果」の
対にして書く。レビュアーへの依頼は「この手順で同じ結果になるか、抜けている
確認はないか」に収斂するので、レビューのゴールを別途書かない。

- 自動で確認したもの: コマンドと結果を 1 行ずつ
- 手で確認したもの: 手順 → 期待する振る舞いを番号付きで
- 確認していないもの: 環境が無い、対象外と判断した、など。正直に書く
  - 「やった」より「やっていない」の境界のほうが重要。レビュアーが補う場所を示す
- ドキュメントのみの変更など確認対象が無いときは、その旨を 1 行書く
- 「特に見てほしい」のような誘導は書かない。読み手がそこに引っ張られる

#### スクリーンショット(MAY・例外)

変更が目に見えるもの(UI、テンプレート、CSS、画面遷移など)のときだけ置く。

- エージェントは画像を撮ろうとしない(MUST)。撮れる環境でも試みない
- 代わりに、見出しと見えるプレースホルダを置く

  ```
  ## スクリーンショット

  (TODO: 変更後の画面を貼る。不要ならこの見出しごと削除する)
  ```

  - HTML コメントにしない。消し忘れが不可視になり、見出しだけ残る
- 埋めるか消すかは人間が決める。「空欄を残さない」原則の唯一の例外
- 目に見えない変更なら見出しごと出さない

#### 補足(MAY)

どの見出しにも収まらないが、知っておくと助かる事実。最後の手段。

- 置く前に、既存の見出しに入らないかを一度検討する
- 「やったこと」に入る内容の逃げ場にしない
- 補足が数項目を超える、毎回同じ種類の内容が入るなら、新しい見出しが要る
  サイン。ユーザーに伝える

#### 関連(MAY)

Issue、ADR、OpenSpec change、関連 PR。コミットの `Refs:` に相当。
OpenSpec の change はパスではなく change 名で指す。

#### フッター(MUST)

本文末尾に `🤖 Generated with [Claude Code](https://claude.com/claude-code)` を
付ける。コミットの `Co-Authored-By` と同じ意味を持ち、**これが無い PR は人間が
手で書いたもの**を意味する。付け忘れは誤った記録になる。重複させない。

### 文体

- 箇条書きを基本にする(SHOULD)
  - 長い段落より箇条書き。文の区切りで改行するのは可
- 幅に合わせた強制改行をしない(MUST)
  - コミット本文の 72 文字ルールは PR に持ち込まない。ブラウザ幅に任せる
- 太字ラベルを使わない(MUST)
  - `**guid台帳**: 説明…` の形は頭に入らない。ラベルを親項目、説明を子項目にする
- 文中の( )補足を子項目に出す(SHOULD)
  - 括弧の開閉を読み手に強いない
- ネストは 4 段まで読める。超えそうなら親の切り方を見直すことも考える
- 絵文字、煽り表現(「大幅に改善」など)、抽象度の混在を避ける

```
Bad:
  - E2E は 404 を返す URL を使い、?a=1&b=2&c=3 が完全な形で届くこと(クォート処理)を購読を成立させずに検証

Good:
  - E2E は購読を成立させずに検証する
    - 404 を返す URL を使う
    - `?a=1&b=2&c=3` が完全な形で届くことを見る
      - クォート処理の確認が目的
```

### 言語

- デフォルトは日本語
- ユーザーの都度の指示 > リポジトリの指示ファイル(CLAUDE.md、AGENTS.md
  など)の指定 > デフォルト、の順で優先する

## 手順

1. **観察**: 以下を確認する。
   - ベースブランチ(通常 `main`)と現在のブランチ
   - `git log <base>..HEAD --format='%h %s%n%b'`。各コミットの本文(Why)を読む
   - `git diff <base>...HEAD --stat`。目に見える変更が含まれるかを判定する
   - `gh pr list --state all --limit 10` で既存 PR のタイトルの調子を見る
   - `openspec/` の有無。あれば進行中の change 名を確認する
2. **なぜを組み立てる**:
   - コミット本文と会話から、PR 全体を貫く判断を取り出す
   - 判断が読み取れない、または指示はあるが理由が無い場合は、**推測を提示して
     確認を取る**。推測を確認なしに本文へ書いてはいけない

     ```
     なぜ はこう理解しています:
       "検知して deny する方式は表記ゆれで抜けるため、allowlist へ転換した"
     合っていますか? 違えば一言ください。
     ```
   - 背景と判断を分ける(判定: PR をやると決める前に書けた文か)
3. **やったことを組み立てる**: 意味のまとまりに分け、それぞれ最終状態を書く。
   まとまりが無関係に多ければ、PR 分割の可能性をユーザーに伝える。
4. **動作確認を組み立てる**: 会話やコミットから実行済みの確認を拾う。
   実行していないものを「実行した」と書かない。分からなければ聞く。
5. **MAY 見出しの取捨**: 該当なしは消す。目に見える変更ならスクリーンショット
   の TODO を置く。
6. **提示**: タイトルと本文をそのまま貼れる Markdown として提示する。
   ファイルへの保存はユーザーが求めたときだけ行う。
7. **PR は作らない**: `gh pr create` を実行しない。ユーザーが明示的に依頼した
   場合でも、まず案を提示し、確認を得てから別の指示として扱う。

## 対象外

- 他者のリポジトリへの PR(相手の規約に従う)
- コミットメッセージの作成は `thinkami-git-commit` を使う
